The Illumio PCE at terminal speed.

Traffic, policy, labels, IP lists, workloads and events in a btop-style terminal UI and a scriptable CLI. Every request is one you caused, every one is counted, and writes happen only when you arm them.

  • EExplainwhich rule allows or blocks a flow, and a jump to it
  • GGeneratethe allow rules an app’s traffic needs, fan-in ports folded
  • DDraftwhat your draft policy would decide, per flow, before provisioning
  • :Readiness → enforcea verdict per app, five steps to full, a watch and an exact rollback
  • mMarkssquelch known noise, flag what matters, locally
  • MBulklabels and enforcement for many workloads, one confirm
  • fFind rulesevery rule that names a label, IP list, service or workload
  • IImpactthe workloads behind a rule, per side, with t to switch it off

Install it Releases Source on GitHub

1Install

One binary. Install it with Homebrew, apt, dnf, an MSI, Scoop or winget, or download it, check it, put it on your PATH.

Homebrew (macOS, Linux)

The repository is its own tap:

$ brew tap alexgoller/illumio-tui https://github.com/alexgoller/illumio-tui
$ brew install illumio-tui

Debian, Ubuntu

Download the .deb (amd64 or arm64) from the release page:

$ sudo apt install ./illumio-tui_0.5.6-1_amd64.deb

RHEL, Rocky, Alma, Fedora

Download the .rpm (x86_64 or aarch64) from the release page:

$ sudo dnf install ./illumio-tui-0.5.6-1.x86_64.rpm

Both packages put illumio-tui in /usr/bin with no dependencies, and are install-tested on Debian 12, Ubuntu 22.04, Rocky Linux 9 and AlmaLinux 8 before each release.

Windows

winget, once the package is merged into winget-pkgs (pending). It installs the MSI below, for the current user.

> winget install AlexGoller.IllumioTUI
> winget upgrade AlexGoller.IllumioTUI     # later, for a new release

MSI (v0.4.1 and later): download illumio-tui-<version>-x86_64-pc-windows-msvc.msi from the release page and double-click it, or install it silently:

> msiexec /i illumio-tui-<version>-x86_64-pc-windows-msvc.msi /qn

It installs for the current user, without admin rights, into %LOCALAPPDATA%\Programs\illumio-tui and adds that folder to your user PATH (open a new terminal). A newer MSI upgrades the installed version in place; uninstalling (Settings > Apps) also removes the PATH entry. The MSI is not code-signed, so SmartScreen may warn when you open it: More info, then Run anyway. Each release installs, upgrades and uninstalls it on a Windows runner before publishing.

Scoop: the repository is its own bucket.

> scoop bucket add illumio-tui https://github.com/alexgoller/illumio-tui
> scoop install illumio-tui
> scoop update illumio-tui     # later, for a new release

From source

With Rust 1.88 or newer:

$ git clone https://github.com/alexgoller/illumio-tui
$ cd illumio-tui
$ cargo install --path crates/illumio-tui

Then point it at your PCE (see Configure) and run illumio-tui for the terminal UI, or illumio-tui health to check the connection from the CLI.

2The terminal UI

Explorer, policy and inventory on five keyboard-driven screens, in the spirit of btop.

Run illumio-tui with no subcommand and it opens on your default profile (--profile prod for another, --theme light for the light palette). Boxed panels with titled borders, dense stats, decision colours, and the API call and byte counters in the header at all times.

Five screens

  • 1Traffic. One filter (f: , AND, | OR, ! excludes, as in env=prod, !app=monitoring or tcp, !22/tcp or !svc:SSH; a port range is 8000-8100/tcp; an exclusion leaves its match out of the whole field; no fqdn: on the source side), one query (r), five views of the result on v; Enter shows a flow’s detail in source, destination and service columns on a wide terminal. / searches, s sorts; a filter that would be expensive asks first.
  • 2Policy. Rulesets and their rules in evaluation order (override deny, allow, deny; allow rules intra-scope, then extra-scope), draft and active on d, pending changes on p, i for the workloads each rule matches.
  • 3Objects. Four tabs: labels, label groups, services and IP lists. u keeps the labels nothing holds, by the PCE’s own usage flags in one request, and names what holds the others: pairing profiles and permissions count as much as workloads and rules. Each IP list shows its size in addresses with exclusions taken out, its ranges and FQDNs, and the draft rules that use it. W (or :used) on any row shows where the object is used in the draft policy before you change or delete it: ruleset scopes, rules (Shop-Prod · #2 · provider · allow, deny and override deny marked, excluded, pending create|update|delete for a draft change not provisioned yet, disabled), the label groups holding it, nested ones via the group, and for a label the pairing profiles that give it (locked when the profile locks that key) and how many workloads carry it: exact from a loaded workload list, else one cached one-row read, so 0 or ≥1 (the PCE’s total header counts the whole collection, not the label’s); Enter on that line opens the exact filtered list. What it needs and is not loaded is read once, on the key press, through the cache; Enter opens the rule on Policy, the group on its tab, or Workloads filtered by the label. Not searched, and the overlay says so: virtual services, enforcement boundaries, container workload profiles.
  • 4Workloads. VEN health columns and a summary line, h unhealthy only, H by severity, t / T jump to Traffic with the workload as source / destination. A workload without a VEN shows enforcement unmanaged, as in the PCE UI, whatever mode the API reports for it (often visibility_only). Local filters, no request: E enforcement, m managed, o offline, u unlabeled (a missing column names the absent scope or role keys), c clears them and h (not the search); a filter line shows what is on and the count. VEN health: the line above the table counts the fleet (VEN 120 · healthy 100 · warning 5 · error 2 · offline 13 · unmanaged 40, in the health colours, of 500 loaded (capped) on a capped list), v cycles a health filter (warning, error, offline), and :ven shows counts per health state, VEN version (newest first, how many behind), enforcement mode and health message; Enter on a row filters the list to it. From the loaded list, no request. f filters by label (app=shop,crm env=prod !role=db: comma any of, space all of, ! excludes, app=- no app label), x groups the list by app and env (the g keys) with VEN health and enforcement per group, Space / z fold, s orders the groups, Enter on a group narrows to it. All local, no request. Space on a workload marks it (●), V marks a group or everything shown, Esc clears; with writes armed L sets labels and M the enforcement of the marked workloads, a group or the row, in bulk.
  • 5Events. Severity-coloured audit events, filtered by severity, type, actor and window. The type filter takes comma-separated terms (sec_policy, rule_set), !term hides (!user.*), * globs the whole type (*.delete) and a leading = is exact (!=user.login hides that type only); Ctrl-N completes the loaded types. warning+ keeps that severity and worse. The actor filter takes the same terms over the Actor column (user:alex@ryte.de, agent:web01, system), each matching the whole actor or the name after its kind: =alex@ryte.de, user:*, !system, !agent:*; Ctrl-N completes the loaded actors. x hides the row's exact type, o shows only it; U hides the row's actor, u shows only it. t lists the types by count (Enter or o only, x hide) and Tab switches it to the actors. All of this filters the loaded events, no request (the PCE is never asked to filter by actor); the header says what is hidden (hiding 3 types · actor !system · 812 of 1,240) and when the PCE's page was full. Enter shows what changed as a diff: only the changed fields, - before and + after, lists diffed by element, hrefs read as names; J toggles the raw JSON; in the detail j/k (or the arrows) step through the events and Ctrl-d/Ctrl-u scroll.

The : prompt takes :traffic, :policy, :objects, :workloads, :events, :iplists, :filter, :window, :profile <name>, :focus, :app, :gen, :unicast, :marks, :used, :export <path>, :writes on|off, :batch, :draft, :active, :save, :filters, :load, :default, :help and :q. ? shows the keys of where you are first; Tab steps through the other groups, a shows them all.

Five views of one traffic result

All five group flows by the same label keys: your profile's scope keys (app,env by default) until g opens the key picker, which also offers all labels.

  • Flows: each side's group and, on Enter, both label sets and the bytes; x groups the flows app by app, by source or destination app, each section with its flow and connection counts (Space / z fold, Enter on a header drills into the app).
  • App-to-app: group pairs with allowed, potentially blocked and blocked counts; o splits each pair by port/proto (one row per allow rule to write); x switches to sections per app (in, out or both), which s orders by connections, app name or flows; Enter drills into a pair's flows.
  • Mesh: user, process, source, destination, service and destination process; u / p hide the user / process column and merge rows.
  • Blocked: blocked and potentially blocked flows by destination group and service.
  • Treemap: each source a box, its destinations tiles sized by connections (b for bytes) and coloured by decision; hjkl move, Enter zooms and drills.

Switching views, grouping, sorting and searching send nothing to the PCE. With writes armed, w turns a blocked flow into a draft allow rule (its Scope, intra or extra, switches on Space and keeps the consumers coherent; a line under them says what they match and warns of an extra-scope rule open to every app); once it is written, the flows on screen are re-evaluated against the draft (one PUT per query, like D), unless a query is running or D would ask first (a cached result, a large window or cap).

F focuses every view on one app: X cycles its inbound, outbound or both directions, Esc clears it. On a truncated result, r re-queries just that app, with its labels in the query.

D shows what the draft policy would decide for each flow, next to the reported decision: blocked → allowed in Flows, would allow counts in App-to-app, a fixed by draft step on d, and draft: N blocked flows fixed in the app screen. It is the PCE’s own Explorer draft view and changes no policy: one PUT on the query you already ran, polls and one download, no new query. D again clears it with no request; Esc cancels it while it runs. On the CLI, --draft.

E explains a flow: the rules the PCE names for it after the draft evaluation, resolved through the loaded draft policy (allow, deny or override deny, ruleset and scope, consumers → providers, services), or no rule allows this flow with the destination’s enforcement and w to draft the rule. It sends nothing; Enter opens the rule on the Policy screen. On the CLI, traffic explain.

A opens one screen for that app: inbound and outbound peers, its workloads with enforcement modes (workloads without a VEN counted as unmanaged) and VEN health, and the rulesets that cover it. It reuses what is loaded; opening it sends at most two requests, and every request is counted in its header.

G there (or :gen) opens the policy generator: the allow rules the app’s own traffic needs, one row per peer with a checkbox, a slider from app, all services to role pairs, the ports seen, rules already in the draft marked exists, and a preview of the flows covered. IP peers that sit in an existing IP list are grouped into one row per list, so the rule names the list rather than a new list per address. A port many peers reach (DNS, NTP, a monitoring agent, a shared service) gets a fan-in line: c turns it into one rule from the built-in Any IP list (checked workload peers keep their own rules, which carry their outbound) or from All Workloads, with its catch and what that rule also allows spelled out. Enter plans every write (IP lists, a ruleset, rule updates and creates) into one confirm; y sends them in order and stops at the first failure, and :batch shows the steps again. On the CLI, illumio-tui gen prints the same proposal and writes nothing.

m marks the row under the cursor: squelch hides known noise, reviewed and accept-blocked dim what you have judged, critical, important and revisit flag what matters. The form is prefilled from the row, previews what it matches, and asks why. Marks live in marks.toml next to the config, apply to every view and the CLI’s traffic commands, and change nothing on the PCE. M shows the squelched rows, :marks lists and edits the marks.

3Workflows

Eight jobs you do on a PCE every week, each as keys and commands, shot on a demo PCE.

Every screenshot and recording below is real: one TUI session and a handful of CLI runs against a shared demo PCE, read-only. Writes were armed only to reach the confirm screens, and every confirm was answered with n. The whole TUI session, from start to the last screenshot, cost 29 requests: the header counts them. The enforcement overlay and policy search shots (v0.4.0) come from a second session with writes not enabled at all: one 24-hour query, D once, the policy and workload loads, 26 requests in all.

1Find and silence noise: flow marks

problem
Nagios checks every host on 5666/tcp. Every view is full of it, and you have judged it long ago.
keys
m on a row, Tab through the form, Enter saves; M shows what is squelched; :marks lists, edits and extends. CLI: marks add, list, export, import.
you see
One squelch on app=monitoring → any 5666/tcp takes 119 flows out of every view (5301 of 5420 flows (119 squelched)). A critical mark puts ● on pos/PCI↔pos/PCI, a revisit puts ◆ on ordering/Development with its 311 blocked flows and expires in 7 days on its own.
PCE cost
None. Marks live in marks.toml next to the config and apply to the TUI and the CLI’s traffic commands alike.
$ illumio-tui marks add --action squelch --src app=monitoring --dst any \
    --service 5666/tcp --comment "Nagios NRPE checks, known and wanted"
$ illumio-tui marks export --format toml > team-marks.toml   # share it; marks import reads it

problem

6From visibility to enforcement: :readiness, :enforce, watch, rollback

problem
Which apps can go to full enforcement today, what stops the others, how do you close the gaps, and how do you undo a move exactly?
keys
:readiness lists every app of the result on screen (s sorts, / searches, D evaluates the draft first); Enter on an app, :enforce <app> or e in the app overlay opens the enforcement overlay: five steps, Tab or 1–5. 1 Readiness the numbers, verdict and warnings. 2 Rules the gaps: G the generator for the app, w an allow rule for the gap, m an accept-blocked mark. 3 Provision the app’s pending changes, P provisions them through the usual preview. 4 Enforce j/k full or selective, v the visibility level, Enter the bulk confirm with the typed count (an app that is not ready asks for the word enforce first). 5 Watch r the blocked-since query, R previews the rollback.
you see
All 23 labelled apps of the demo PCE are needs rules over the last 24 hours; infra-mgmt/Production is closest at 90.5%. Its overlay: two workloads in selective, one gap (7680/tcp from pos/Staging, 3 flows), two pending changes, and step 4 blocked: the plan 2 workloads: 2 selective → full, the record directory, and writes off.
PCE cost
:readiness reuses the query on screen and its D; it read the workloads, pending changes and draft rulesets once (3 requests, cached). Opening the overlay: 0. Writes are the bulk move and its change record, exactly as the CLI writes them. r on Watch is one query, only when pressed; nothing refreshes by itself.

The same job on the CLI, for scripts and cron: readiness for every app, readiness --app X for its gaps and pending changes, enforce X --to full --dry-run (exit 6 until ready) then --yes --confirm-count N, enforce X --watch (exit 7 when something is blocked since), enforce X --rollback. Over 7 days, all apps: one Explorer query with the draft evaluation, 25 requests, 43 s; one app: 14 requests, 9 s; --watch: one query, 8 requests.

7Find rules fast: f, t, I

problem
Which rules, in any ruleset, touch pos or ordering? Which workloads does one of them really cover, and can you switch it off for a test?
keys
On Policy, f searches every loaded ruleset: app=ordering,pos (a label in a scope, consumer or provider, directly or through a label group; comma is any of), ipl:Corp, svc:443/tcp or svc:PostgreSQL, wl:web01, href:, disabled, enabled, deny, allow, intra, extra; terms apart by spaces all hold. scope:, src: and dst: say where a label sits (src:/dst: also take ipl:, wl: and all; scope:global), !env=prod finds exclusion actors, a leading - leaves a term out: src:role=web dst:role=db extra (extra-scope rules from web to db), scope:app=payment -svc:443/tcp (payment rules not covering 443), src:!env=prod (consumers that say All except prod), src:all -deny (allow rules open to All Workloads). The header says how many matched of the rules loaded. Enter opens the rule in its ruleset, c clears. I lists the workloads a rule matches, providers first, Tab the consumers, Enter jumps to one on Workloads. t enables or disables a rule or ruleset (a draft change, writes armed). CLI: policy search, policy rules impact <href> --list providers|consumers, policy rules enable|disable, policy rulesets enable|disable.
you see
Search · app=ordering,pos: 26 rules across 7 rulesets, in evaluation order, with scope, consumers, providers, services and the rule’s own enabled ((ruleset off) when its ruleset is disabled). PCE cost
None: search and I use the loaded policy and the cached workload list (i reads it once if no screen has). The CLI search is one rulesets read and the name index, cached. t is one PUT through the usual confirm.

8Small things

  • Ctrl-U empties the line in every text input, as in a shell: the filter editor, the mark and rule forms, the : prompt. Ctrl-N / Ctrl-P complete labels, IP lists, services and values without a request.
  • Shell completions for bash, zsh and fish ship with the Homebrew formula and the .deb/.rpm; otherwise illumio-tui completions zsh > ~/.zfunc/_illumio-tui (PowerShell: illumio-tui completions powershell | Out-String | Invoke-Expression in your profile). Every subcommand, flag and enum value completes, and --profile completes your profile names. Labels, apps, hostnames, services, IP lists and label groups complete from a per-profile names cache that the list commands, the TUI and illumio-tui completions refresh fill (--clear deletes it; completion_cache = false keeps PCE names off disk). The cache needs a profile from the config file with its own host and org_id: a PCE named by --host/--org-id or PCE_HOST/PCE_ORG_ID writes none. Completion never contacts the PCE.
  • :export <path> writes the table on screen as CSV, the same format as the CLI’s --csv.
  • Apple Terminal garbles 24-bit colour before macOS 26, so there the theme is mapped to the xterm 256 colours by itself; ILLUMIO_TUI_COLORS=256 or truecolor overrides it anywhere.

One app, start to finish

  1. illumio-tui readiness ranks every app; infra-mgmt/Production is closest, 90% covered.
  2. readiness --app infra-mgmt/Production: the gaps are 7680/tcp from pos/Staging and 8080/tcp out; two rulesets wait for provisioning.
  3. In the TUI, r once for 24 hours, m squelches the Nagios noise, D overlays the draft.
  4. E on the 7680/tcp flow: no rule allows this flow. E on a DNS flow: the activedirectory rule, Enter to see it.
  5. A, G: NTP from 7 peers folds into one Any rule with c, Space adds pos/Staging, p says 27 of 27 flows covered, Enter and y write the ruleset and 3 rules; P in Policy’s pending overlay provisions them.
  6. :readiness (or readiness --app) again until ready; :enforce infra-mgmt/Production, step 4, Enter and the typed count (CLI: enforce --to full --dry-run, then --yes --confirm-count 2).
  7. enforce --watch from cron the next morning (or r on step 5): exit 0, or exit 7 and the tuples; R or --rollback if it has to go back.

On the demo PCE the recordings stop at step 5’s confirm with n, and at step 6’s plan and dry run: it is shared.

4CLI: getting started

From install to a useful answer, in eight short steps.

1. Connect

Install the binary, then give it a PCE: a dotenv file with the illumio-mcp-server names, or a profile in ~/.config/illumio-tui/config.toml (see Configure).

$ cat pce.env

PCE_ORG_ID=1
API_KEY=api_xxxxxxxxxxxx
API_SECRET=xxxxxxxxxxxxxxxx
$ illumio-tui --env-file pce.env health
field   value
ok      true
host    demo100.illum.io
org_id  5636114
status  [{"generated_at":"2026-10-19T21:21:07+00:00","listen_only_m…

Explorer, without the clicking

traffic query submits the PCE's asynchronous Explorer query, polls with backoff, downloads the result, flags truncation, and resolves every label href to key=value.

Filters read like you think: app=web, ip:10.0.0.5, ipl:NAME, wl:HOST, fqdn:NAME. A comma means AND, repeating the flag means OR. Add --exclude-src, --exclude-dst, --exclude-service, --port, --proto, --process and --decision as needed: --dst env=prod --exclude-src app=monitoring --exclude-service 22/tcp goes into Explorer’s own exclude lists, at no extra cost. A port range is FROM-TO/PROTO with tcp or udp, both ends included: --exclude-service 8000-8100/tcp, or --port 8000-8100 --proto tcp to include it. --exclude-service svc:NAME takes a service object’s ports and port ranges. fqdn: is a destination filter only: on --src or --exclude-src it exits 2. An unknown label value fails locally, before the PCE sees anything.

--group app,env folds flows into label pairs; --blocked keeps blocked and potentially blocked flows, grouped by destination group and port. traffic groups prints one row per source and destination group with connections, bytes and decisions (--services: one per group pair and port/proto); traffic mesh one row per user, process, source, destination, service and destination process, with --no-user and --no-process to merge. --keys picks the label keys (default: the profile's scope keys). --app shop/prod --direction in spends the cap on one app: its labels go into the query (two queries for both, merged). flows counts flow records; conns and bytes are the lifetime counts of those records, as in the PCE UI, and JSON and CSV add them per decision (allowed_conns, pot_blocked_conns, blocked_conns, unknown_conns). --transmission unicast (or broadcast, multicast; :unicast in the TUI) leaves out the other kinds in the query itself; the default keeps every kind, where workloader counts unicast only.

illumio-tui app shop/prod prints the app overlay as one JSON envelope for agents: workloads and VENs, peers and policy; --table and --csv --section print it per section.

illumio-tui gen shop/prod prints the generator's proposal: the target ruleset, one row per peer (kind intra, app, ip_list with its ip_list and ips, ip, workload or folded_ips), the rules with their exact PCE bodies, the IP lists to create, the fan-in ports under consolidations (--consolidate 5666/tcp=any|all switches one to its single rule) and a coverage preview. A capped result exits 2, an incomplete one 4.

--impact on policy rules counts the workloads each rule matches as providers and consumers, across the ruleset's scopes, label groups and exclusions, from one cached workload read; iplists gives every list its size.

Agents and scripts: schema and --fields

JSON is the default whenever stdout is not a terminal, so an agent gets the envelope without asking. Every envelope names its schema in meta.schema; illumio-tui schema lists them all (plus the shared envelope, meta and error), and illumio-tui schema workloads ven-summary prints that envelope’s JSON Schema (draft 2020-12). No profile, no request. Every envelope the CLI’s tests read is checked against its schema, so the schema is the contract.

$ illumio-tui schema
$ illumio-tui schema workloads ven-summary     # or a schema name: write, envelope, meta, error
$ illumio-tui workloads --label app=shop --fields hostname,health,labels.value --json
$ illumio-tui labels --csv --fields key,value > labels.csv

--fields keeps only the named fields of data (each element of a list), dotted paths reach into nested objects and through lists and keep the nesting; meta is never filtered. JSON names come from the schema (of the shape the flags print). With --csv the names are the column headers, not the JSON names, picked and ordered; schema COMMAND lists them in its $comment. Either way the names are checked before any request (exit 2, listing the valid ones), with a table it is exit 2, and it never changes what is asked of the PCE. Failures go to stderr as {"error": {...}} with the exit codes above; argument errors clap catches print its usage text, exit 2.

7Writes, on purpose

Off unless the profile says yes. Planned, shown, confirmed, audited.

illumio-tui writes labels, IP lists, services, unmanaged workloads, pairing profiles (CLI), and policy: rulesets, allow and deny rules, provisioning, and the labels of VEN-managed workloads. None of it happens by accident:

  • The profile gates it. Without writes = true (or ILLUMIO_WRITES=1) every write is refused with exit code 6, even a dry run.
  • The CLI needs --yes. --dry-run prints the exact method, path and JSON body and sends nothing; with neither flag nothing is sent. Nothing is ever retried.
  • The TUI starts with writes off. :writes on arms them for the session, the header shows ✎ writes, and n / e / x create, edit and delete (Workloads: X, as x groups there). The confirm overlay shows the summary, METHOD path and the whole body before y sends it once.
  • Bulk changes guard themselves. L / M on Workloads and workloads enforce / relabel on the CLI change many workloads in bulk_update requests of 100, after one confirm listing every change. Full or selective on several workloads, or any change to more than 25, needs their count typed (--confirm-count), and the CLI needs a filter or --all; d asks the draft policy what their traffic in and out would block, only when pressed. Before sending, a fresh read skips every workload changed since the plan; a chunk with a failure or an unknown outcome stops the rest, and each chunk’s audit entry lists every workload’s outcome.
  • Pending changes are diffed. On Policy, p lists what waits for provisioning; Enter shows a draft IP list, service or ruleset against active, and P provisions the marked entries after showing the exact change_subset.
  • Every sent write is audited to ~/.local/state/illumio-tui/writes.jsonl (mode 0600) with the body sent and the status received.
  • Updates send only what changes, and carry untouched list entries through exactly as the PCE returned them.
$ illumio-tui labels add app=web --yes
$ illumio-tui iplists update Corp --add-range 10.2.0.0/16 --dry-run
$ illumio-tui policy rules add Web-Tier --provider app=web --consumer iplist:Corp --service 443/tcp --dry-run --impact
$ illumio-tui policy provision --all --dry-run
$ illumio-tui workloads enforce full --label app=shop --label env=prod --yes --confirm-count 14
$ illumio-tui workloads relabel --set env=prod,role=- --label app=shop --dry-run
$ illumio-tui pairing-profiles create shop-prod --label app=shop --label env=prod --enforcement visibility_only --lifespan 7d --lock app,env --dry-run
$ illumio-tui pp delete shop-prod --yes

pairing-profiles create sends the name plus only the flags given, so the PCE's defaults apply to the rest; a taken name or an unknown label is exit 2 before anything is sent. The PCE locks every setting whose lock is not sent: --unlock names the ones to leave changeable at pairing. Pairing keys are left out: an activation code is a secret.

Rules use a compact token grammar: app=web, group:NAME, iplist:NAME, workload:HOST, all, and ! to exclude. --impact on a rule write reports the workloads it will touch before anything is sent. The README has the full reference.

Profiles

Write one from a dotenv file (- reads a paste from stdin) or flags; local, no request:

Flags override imported values. The secret comes from the env file, --api-secret-stdin, --api-secret (lands in shell history) or --api-secret-cmd (wins, no plaintext stored); a plaintext secret is stored as api_secret in a file of mode 0600. --force updates an existing profile's connection settings and keeps the rest (limits, labels, generator); the first profile becomes the default. Single-quote a value with a $: dotenv expands $VAR. The secret is never printed.

api_secret_cmd fetches the secret from your password manager at run time; keep it non-interactive, because :profile runs it while the TUI owns the terminal. Switch profiles with profile use, --profile or :profile.

The label model

Rulesets are scoped by scope_keys (app, env by default) and rules select tiers by tier_key (role). The traffic views, traffic groups, traffic mesh and traffic query --blocked group by the scope keys, and the w rule form pre-fills from both. Labels print in scope-key order, then the tier key, then alphabetically.

ignore_keys hides housekeeping keys from label columns and the g picker; JSON output and the workload edit form keep them, the Labels tab shows them on i, and a scope or tier key is never ignored.

Event types hidden by default

exclude_types lists event types the Events screen and events hide unless asked: each a substring, a * glob or an exact type (=user.login), added as a !term to the type filter. The TUI's Type field starts with them (f drops one for the session); events --all-types shows every type. The tool reads this setting and never writes it.

Saved filters

[profiles.<name>.filters.<screen>.<filter>] holds named filters for Traffic, Policy, Events and Workloads in the f editors' text (a policy filter is one search query). :save and --save-filter write them, keeping every other setting; one that does not parse fails only when used. Names: letters, digits, . _ -, up to 64, not starting with -.

[profiles.demo.filters.traffic.prod-blocked]
src = "env=prod"
dst = "!app=backup"
service = "!53/udp, 8000-8100/tcp"
decisions = ["blocked", "potentially_blocked"]
window = "7d"                      # left out: the window in force stays

[profiles.demo.filters.policy]
deny-prod = "dst:env=prod deny"

[profiles.demo.filters.events.noise-free]
type = "!agent.*, !=user.login"
actor = "!system"
severity = "warning+"

[profiles.demo.filters.workloads.prod-unenforced]
labels = "env=prod"
enforcement = "visibility_only"
managed = true

[profiles.demo.filters.workloads.unhealthy-vens]
health = ["warning", "error", "offline"]
ven_version = "23.2.*"              # exact, or a * glob

[profiles.demo.filter_defaults]       # one per screen, a saved filter's name
traffic = "prod-blocked"
events = "noise-free"

filter_defaults names each screen's default: the TUI applies it at startup and after :profile, before the screen loads and without an extra request; the CLI only with --default-filter. One that names no filter or does not parse is ignored with a warning. Removing a filter that is a default removes the default. An events filter's type terms get exclude_types on top, so both apply.

The generator

ruleset_name names a ruleset the policy generator creates, as a template over the scope keys (RF-shop-prod); every {key} must be a scope key and every scope key must appear. consolidate_min_peers is how many inbound peers on one port make it a fan-in line; DNS, NTP, Kerberos, LDAP, SMB, syslog, SNMP and monitoring-agent ports need 3.

9Gentle on the PCE, by construction

Your PCE is shared, expensive and important. This tool treats it that way.

Most tools that hammer a management plane do it by accident: a refresh loop nobody asked for, a retry storm, an Explorer query over ninety days that someone fired off to see what happens. illumio-tui is built so that none of that can happen quietly. Every request is caused by you, throttled, cached where it can be, counted, and shown back to you.

  • 2 req/s, burst 5One token bucket shared by every request (requests_per_second in the profile). 429 and 503 pause the whole client with exponential backoff and jitter, honouring Retry-After. POSTs are never retried.
  • Counted, alwaysEvery call and byte goes into meta.api_calls and meta.bytes, and into the TUI header. You always know what you spent.
  • Cached 15 / 5 / 1 minLabels, label groups, IP lists and services for 15 minutes; policy and workloads for 5; events for 1. One traffic result is kept until the filter changes; draft decisions for 2 minutes.
  • 5 requests to startThe TUI opens with health plus the four object lists. The first visit to Workloads and to Events costs one request each; going back costs none.
  • No auto-refresh by defaulta turns it on per screen, never faster than every 60 seconds, with a countdown; it switches itself off after a failed refresh.
  • 24 h, 10 000 rowsExplorer queries default to a 24-hour window and a 10 000-row cap, at most 200 000. Truncation comes from the PCE's own row count and is always reported; B and --backfill re-run the window at a larger cap, one query per rung, asking above 10 000.
  • Draft view on requestD and --draft ask the PCE to re-evaluate your own query against draft policy: one PUT on that query resource, polls and one download per query, cached. It changes no policy, so it needs no armed writes; it is never sent without the key, the flag, or a successful write of yours: that re-evaluates the draft decisions on screen (or a w rule's flows) once, visibly, with Esc on Traffic to cancel, and only where D would run without asking. A draft answer a write overtook is never cached.
  • --yes above 7 days or 10 000 rowsExpensive queries stop with exit code 2 and tell you why, until you confirm on purpose.
  • --dry-runPrints the exact Explorer request body and sends nothing. See the query before the PCE does.

10Roadmap

New in the 0.5 line (v0.5.0 to v0.5.6): PCE names in shell completion from a local per-profile cache, with completions refresh (#64); the intra- and extra-scope rule form, with what a rule means and warnings as you type (#65); profile add from an env file or flags (#66); event type filters with excludes, exact types and per-profile defaults (#67); the policy search grammar with scope:, src:, dst: and negation (#68); saved filters (#70) and a default filter per screen (#74); VEN health on Workloads (#72); events by actor (#71); a schema command and --fields for agents and scripts (#73); where-used for labels, groups, IP lists and services (#75); pairing profiles in the CLI (#76). The changelog has the notes of every release.

Open now:

  • winget: automatic submissions once the first winget-pkgs PR is merged (#69).
  • An idea: an MCP mode, the same read and write layer, with its throttle and guards, as tools for an agent.

Every idea from the list in issue #5 has shipped. New ideas are welcome in the issue tracker.

What it leaves to others: workloader is the established batch tool for the PCE, and the two work side by side. illumio-tui is for interactive analysis, rule drafting and agents; for bulk import and export, automated labelling, VEN lifecycle, rule and port usage reports and running across many PCEs, use workloader.

Suggestions and bug reports are welcome in the issue tracker.
